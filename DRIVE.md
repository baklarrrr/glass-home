# Drive: phone GPS speed

Drive uses standard `navigator.geolocation.watchPosition()` in the existing glasses web app. Start GPS is a deliberate action, with no extra custom parked-confirmation dialog. The browser/OS controls the permission prompt; the app never bypasses it. Re-entry in the same page resumes only if the browser reports an existing grant. Missing permission-query support requires another deliberate Start. Leaving Drive or hiding the page releases the watch. Menu auto-hide does not stop an enabled feed. Detailed planning, review and message composition keep their existing interaction safeguards.

The value is reported GPS ground speed, converted from metres per second to kilometres per hour. It is an estimate, not vehicle ECU telemetry, a vehicle instrument, or live navigation. No OBD connection is assumed. A saved route can be followed for the next turn (see "Compass and saved-route guidance"); it is never live navigation. Platform driving restrictions remain in force.

The display accepts only finite nonnegative reported speed, finite nonnegative position accuracy no worse than 50 metres, and acquisition time less than five seconds old and not in the future. Values above 100 m/s are rejected as implausible for this road-oriented view. These are explicit product filters, not SDK thresholds or a guarantee of speed accuracy. The W3C API does not expose speed uncertainty or mock-location provenance. It cannot certify sensor truth. Null, invalid, denied, stale, disconnected and unsupported states display a dash; zero is shown only when the source reports zero. No speed is derived from coordinates.

Coordinates are neither retained nor transmitted by this feature. Current speed, acquisition/arrival clocks and a bounded connection summary exist only in page memory. GPS details shows build GPS 27, an explicit current status, callback count, last fix acquisition date/time/accuracy/speed-present flag, last API error code/time/request number, permission/policy and watch visibility. The fixed acquisition time cannot become a frozen age when details remains open. A historical error is not the current state. It stores no coordinates, identifiers, raw error text or location history, and sends nothing. There is no new server, account or background permission. `enableHighAccuracy` is a hint. No camera, microphone or motion permission is requested.

The API timeout remains ten seconds. Error code 3 is labelled as a timeout, not ongoing loading; it does not prove a permission denial or a disconnected phone. A separate twelve-second no-callback notice covers runtimes that return neither callback. Neither stops an otherwise active watch, so a later fix can recover. Retry explicitly replaces the current watch once; there is no retry loop. Stop remains available. These corrections do not establish working hardware reception. The caller can compare GPS details across runtimes without uploading location.

Ordinary controls reveal deliberately and hide after eight seconds without input. GPS details/help has no idle-dismissal timer; explicit Back or navigation leaves it. Suspending the page does not dismiss details. While a location request could be awaiting an unconfirmed permission, ordinary-control hiding pauses as well; a known grant or resolved callback releases that hold. Incoming data does not reveal controls or move focus. Real agent Send remains disabled. The worker update waits for normal client closure and never forces an open HUD to reload.

Speed self-check (`drive/speed-check.js`, shared by Studio Drive and the older Drive page). With no speed on screen, Drive says why in two short amber lines, but only for a hard fault of the glasses' own location with nothing healthy behind it: refused ("Glasses location not allowed"), no location in this app, a speed that was lost ("GPS speed lost"), a timeout, or no fix. The second line says what backs it up: "Pair your phone", "Compare the code on your phone" (compare, not accept: the wearer taps Yes on the phone only when the numbers match), "Resume the phone link", "Phone link unavailable", "Phone not answering" or "No signal to phone" (the glasses cannot reach the brokers at all). A phone that is linked or still being found is the speed source to come, so the glasses' refusal is not the story and nothing is added. On the older page that also holds at launch (the saved link is still being read) and for eight seconds after the display wakes or the signal returns: the phone has just been asked again and only then counts as silent. Calm states keep each screen's usual words: GPS not started, still asking, a reading that is only rough, has no speed (parked) or is unusable (these come and go by themselves, often just after Start), and a status nobody knows. Beside directions the older page's corner is narrow, so its two long first lines have short forms ("Glasses GPS refused", "No GPS in this app"). The exact status stays in GPS details ("Now: Location permission not granted").

The check only reads state. It starts no GPS, retries nothing, asks for no permission and changes no filter, so Start and Retry stay deliberate and there is still no retry loop. A speed that is not live is a dash, never an old number, and a missing module leaves the earlier wording unchanged. What it does not cover: a phone link that stays "waiting" or "ready" for ever because the Journal was killed after one reply (the link state never expires; the older page falls back to "ready" after 30 seconds of silence, and a silent-phone detector needs the time of the last message from the phone, which Studio's `drive-phone.js` does not expose yet, so Studio Drive cannot say "Phone not answering"); a link stuck at "connecting"; a phone that sends frames with no speed (by design the Journal sends speed only while it is checking or recording a drive). Studio's "Phone speed expired" is amber and stays amber until the speed returns, because the page cannot tell a parked car from a dead sender. The older page's pairing screen still says "Accept this code", and Studio Drive shows the pairing code only in GPS details. Meta's documentation says the glasses have no satellite receiver of their own and take a location through the paired phone, with speed and heading possibly null, so the glasses' own speed is best effort and the phone's GPS through this link is the dependable source.

Unit checks: `node --test tests/drive-location.test.cjs tests/drive-help.test.cjs drive/tests/speed-check.test.cjs`. The help tests run the actual shell/feed/render functions with in-memory clocks and a minimal DOM; they are not browser or optical checks. Browser checks (Playwright, 600×600): `node drive/tests/browser.cjs [outDir]` for the older page and `node drive/tests/studio-browser.cjs [outDir]` for Studio Drive. They use synthetic geolocation callbacks, block external requests and play the phone with throwaway test keys, never a real pairing. Browser checks do not establish physical-glasses acceptance or a real GPS stream. Parked wearer acceptance is tracked separately from web publication.

## Compass and saved-route guidance (11 Nov 2026)

Bakar, 11 Nov 2026: "I also want to be able to navigate, have a compass, have a speedometer ... I'm a professional driver" and "get rid of those CHECKS to see if im driving ... GONE AND REMOVED."

- **Compass tape** (`drive/guide.js`, `tape`): the GPS course over the ground under the unit line: ticks every 15 degrees, the compass points either side, north in the accent colour and never dimmed, and one readout at the needle ("E 090°"). It is the way the car moves, not the way the wearer looks. Below about 7 km/h the feed gives no course and the tape is not drawn: never an old heading. It always keeps its room, so the speed does not move when it comes and goes.
- **Saved-route guidance** (`drive/guide.js`, `Guide`): with no directions from a phone, the turn line shows the next turn along the route the PC saved (`relay/route.py` adds `gl`, the road as latitude/longitude pairs within about 12 m; `gs`, every turn as metres from the start plus words; `gm`, the road's length). The glasses work it out from their own location.
  - It starts only after three fixes in a row on the line and moving the way the road runs there (course within 60 degrees), and only for a route saved in the last 18 hours. Crossing the route, or driving it the other way, starts nothing.
  - Three fixes off the line: "Off the saved route" in amber, and how far. 2.5 km off or five minutes off: it stops quietly. Three fixes going back along it: it stops, and stays stopped for that route.
  - A fix older than five seconds or rougher than 50 m never moves it. Beside anything but a live reading the turn is replaced by "Saved route paused / Waiting for location", and by nothing once GPS is stopped.
  - "Arrived" shows for two minutes, or until the wearer is 150 m from the end.
  - The words: distance first ("350 m · Turn left · Second Ave"), one line always (a long name is cut), the distance larger under 300 m. The line under it says what this is: "Saved route · not live · 850 m to go". There is no rerouting and no traffic.
- **No press to start:** opening Drive starts the speed by itself when location is already allowed (the feed's own resume path, so no permission prompt can come from looking at Drive). A Start that worked is remembered on the glasses (`localStorage`, `bakar.drive.gps`) and made again next visit even where the runtime cannot report the permission. A deliberate Stop holds until the next Start and clears that memory.
- **Course without a heading:** where the glasses' location gives no heading, the course is the bearing between two fixes at least 12 m apart, used for the tape and for guidance, and dropped after five seconds without fresh movement. A reported heading always wins.
- **Privacy:** the fix is read as it arrives. Page memory holds metres along the route, metres off it, and the one earlier fix needed to work out the direction of travel, replaced as the car moves. Nothing is written to storage and nothing is sent. The route itself reaches the glasses inside the same encrypted snapshot as before.
- **No parked check:** `parked.js` no longer asks anything; the Route tab and Drive controls open at once. The old dialog is in git history.
- **Checks:** `node --test drive/tests/guide.test.cjs` (27 cases) and the auto-start and saved-route sections of `node drive/tests/studio-browser.cjs [outDir]` (frames `s13` to `s17`). Not checked: real optics, real GPS on the glasses, a real drive.
- **Limits:** a route is made on the PC (`route.py "Place"`, or the AIs' `glasses_route` tool) before setting off. Picking a destination from the car or rerouting needs an iPhone-side sender; that is not built.
