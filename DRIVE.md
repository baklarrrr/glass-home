# Drive: phone GPS speed

Drive uses standard `navigator.geolocation.watchPosition()` in the existing glasses web app. Start GPS is a deliberate action, with no extra custom parked-confirmation dialog. The browser/OS controls the permission prompt; the app never bypasses it. Re-entry in the same page resumes only if the browser reports an existing grant. Missing permission-query support requires another deliberate Start. Leaving Drive or hiding the page releases the watch. Menu auto-hide does not stop an enabled feed. Detailed planning, review and message composition keep their existing interaction safeguards.

The value is reported GPS ground speed, converted from metres per second to kilometres per hour. It is an estimate, not vehicle ECU telemetry, a vehicle instrument, or live navigation. No OBD connection is assumed. Saved routes remain parked planning previews. Platform driving restrictions remain in force.

The display accepts only finite nonnegative reported speed, finite nonnegative position accuracy no worse than 50 metres, and acquisition time less than five seconds old and not in the future. Values above 100 m/s are rejected as implausible for this road-oriented view. These are explicit product filters, not SDK thresholds or a guarantee of speed accuracy. The W3C API does not expose speed uncertainty or mock-location provenance. It cannot certify sensor truth. Null, invalid, denied, stale, disconnected and unsupported states display a dash; zero is shown only when the source reports zero. No speed is derived from coordinates.

Coordinates are neither retained nor transmitted by this feature. Current speed, acquisition/arrival clocks and a bounded connection summary exist only in page memory. GPS details shows build GPS 27, an explicit current status, callback count, last fix acquisition date/time/accuracy/speed-present flag, last API error code/time/request number, permission/policy and watch visibility. The fixed acquisition time cannot become a frozen age when details remains open. A historical error is not the current state. It stores no coordinates, identifiers, raw error text or location history, and sends nothing. There is no new server, account or background permission. `enableHighAccuracy` is a hint. No camera, microphone or motion permission is requested.

The API timeout remains ten seconds. Error code 3 is labelled as a timeout, not ongoing loading; it does not prove a permission denial or a disconnected phone. A separate twelve-second no-callback notice covers runtimes that return neither callback. Neither stops an otherwise active watch, so a later fix can recover. Retry explicitly replaces the current watch once; there is no retry loop. Stop remains available. These corrections do not establish working hardware reception. The caller can compare GPS details across runtimes without uploading location.

Ordinary controls reveal deliberately and hide after eight seconds without input. GPS details/help has no idle-dismissal timer; explicit Back or navigation leaves it. Suspending the page does not dismiss details. While a location request could be awaiting an unconfirmed permission, ordinary-control hiding pauses as well; a known grant or resolved callback releases that hold. Incoming data does not reveal controls or move focus. Real agent Send remains disabled. The worker update waits for normal client closure and never forces an open HUD to reload.

Speed self-check (`drive/speed-check.js`, shared with the older Drive page). With no speed on screen, Drive says why in two short amber lines, but only for a definite fault with nothing healthy behind it: the glasses' own location refused, unsupported or lost, and no phone link that is, or is about to be, the speed source. The first line names the fault ("Glasses location not allowed", "GPS speed lost"), the second what backs it up ("Pair your phone", "Accept the code on your phone", "Phone link stopped", "Phone link unavailable", "Phone not answering"). Calm states keep their usual words: GPS not started, still asking, and a phone that is linked or still being found (the glasses' own location is then not the story). A phone speed that has gone dead shows "Phone speed expired" in amber. The check only reads state. It starts no GPS, retries nothing, asks for no permission and changes no filter, so Start and Retry stay deliberate and there is still no retry loop. The exact status stays in GPS details ("Now: Location permission not granted"). A missing module leaves the earlier wording unchanged.

Unit checks: `node --test tests/drive-location.test.cjs tests/drive-help.test.cjs drive/tests/speed-check.test.cjs`. The help tests run the actual shell/feed/render functions with in-memory clocks and a minimal DOM; they are not browser or optical checks. Browser fixtures must use synthetic geolocation callbacks, block external requests and avoid pairing. Browser checks do not establish physical-glasses acceptance or a real GPS stream. Parked wearer acceptance is tracked separately from web publication.
